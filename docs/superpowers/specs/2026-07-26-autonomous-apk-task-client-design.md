# Autonomous APK Task Client Design

**Date:** 2026-07-26
**Status:** Draft for review
**Scope:** Replace runtime SSH/ADB command delivery with an APK-initiated HTTPS task loop.

## Goal

Allow each VMOS device to continue mobile touch work after the Mac, SSH tunnel, or ADB connection disappears. ADB remains a bootstrap and diagnostics channel only. The system must preserve durable target coverage, visible action evidence, idempotency, priority-task interruption/resume, and the capacity target of 10,000 unique targets per 24 hours.

## Current Problem

The current device-side APK executes commands sent through a local loopback helper over SSH and ADB. ADB forward ports are process-global; a health probe can replace a worker's forward and cause `DeviceSideUnavailable`. Any Mac/network interruption stops command delivery. This transport is unsuitable as the production control plane.

## Selected Architecture

The backend remains the source of truth for target pools, account/device mapping, eligibility, quotas, immutable action plans, leases, priority queues, coverage, and metrics. The APK becomes an autonomous, outbound-only client:

```text
Task service / durable database
        ▲ HTTPS pull, heartbeat, result outbox
        │
        ▼
APK client (one account/device)
  ├─ local durable queue and checkpoint
  ├─ existing Accessibility executor
  ├─ lease/fence validator
  ├─ idempotent result outbox
  └─ reconnect/backoff controller
```

The APK never receives TikTok credentials, cookies, browser storage, or arbitrary shell commands. It receives typed task envelopes and reports typed evidence.

## Responsibilities

### Backend

- Register and revoke device identities.
- Issue short-lived scoped access tokens and task leases.
- Allocate normal and priority work without duplicate device claims.
- Persist the immutable plan, target identity, selected video/action, quota reservation, and all terminal evidence.
- Count a visit only after identity, route, and post-action evidence pass.
- Keep the main-batch cursor server-side so an interrupted priority batch can resume exactly.
- Expose fleet health, queue depth, latency, deferred/uncertain counts, and per-account coverage.

### APK

- Authenticate with a device-scoped token stored in Android Keystore.
- Pull a bounded queue of typed envelopes over HTTPS.
- Persist each envelope before execution and persist phase transitions after every visible checkpoint.
- Execute only the existing business-plan phases through Accessibility UI.
- Upload results through an idempotent outbox; retry transport failures without repeating a completed click.
- Send heartbeats containing app version, account binding, current phase, queue depth, last result time, and client/network latency. Do not include message text or credentials.
- Stop claiming new work when the lease is expired, identity binding changes, or the local circuit breaker opens.

## Task and Lease Contract

Every task has a server-generated `task_id`, immutable `plan_id`, `device_id`, `account_id`, target identity, policy version, lease ID, lease expiry, and monotonically increasing session epoch. The plan contains the selected route/video/action and quota reservation; the APK does not reinterpret eligibility or choose a different action.

Every command and result has an immutable `attempt_id` and `idempotency_key`. The server accepts a result once, rejects stale epochs, and treats duplicate uploads as a read-only replay. `uncertain` remains unresolved until the single reconciliation path or lease expiry; it is never immediately clicked again.

A fresh database may start its own local counters, but those counters are never used as global fences. Global fencing is `(device_id, session_epoch, lease_id)`, generated by the backend and persisted by the APK.

## Queue, Offline, and Priority Behavior

- The client prefetches a small bounded window (default 20 tasks, configurable by policy) and never claims unbounded work.
- A temporary network outage allows completion of already leased tasks until their lease deadline. New claims stop after the deadline.
- Results are written to the local outbox and uploaded when HTTPS returns. Backoff is exponential with jitter.
- Priority tasks are returned before normal tasks at the next target boundary. The APK never interrupts an in-flight profile/video/action phase.
- After priority completion, the client requests the next normal task using the server's saved cursor.
- A crashed or restarted client reloads only unfinished local envelopes and reconciles them by idempotency key before continuing.

## Security and Operations

- Device API is HTTPS-only with certificate validation; no inbound port is required on the VMOS device.
- Tokens are short-lived, device-scoped, revocable, and stored in Android Keystore. Provisioning is a one-time bootstrap operation.
- VMOS OpenAPI is used for instance lifecycle, APK installation, and recovery, not per-target clicks.
- ADB is limited to bootstrap, APK upgrade, calibration, and diagnostics. Production health checks use the device HTTPS heartbeat and must never create or replace ADB forwards.
- Two consecutive heartbeat failures pause new claims; repeated result-upload failures open the device circuit breaker and surface an operator alert.

## Migration Stages

1. **Transport isolation:** make current diagnostics read-only and prevent health probes from sharing worker ADB forwards.
2. **Backend contract:** add device registration, token rotation, lease claim, heartbeat, result upload, and priority-queue endpoints with contract tests.
3. **APK client:** add local queue/checkpoint/outbox, HTTPS polling, epoch validation, and reconnect logic while retaining the current Accessibility executor.
4. **Shadow mode:** pull and validate plans without clicking; compare APK plans with backend plans and measure heartbeat reliability.
5. **Single-device acceptance:** run 20-target, 100-target, and 30-minute tests with Mac/ADB disconnected after startup.
6. **Dual-device and fleet acceptance:** run two-device 30-minute tests, then seven-device endurance and 24-hour coverage tests.
7. **Cutover:** disable runtime ADB command delivery; keep ADB only in the provisioning and diagnostics tools.

## Acceptance Gates

- After startup and provisioning, disconnect the Mac and ADB tunnel; the device completes its leased queue and later uploads all results.
- Device restart resumes without duplicate visible actions.
- Replayed result uploads do not create duplicate visits or interactions.
- Priority work executes at a target boundary and normal work resumes from the saved cursor.
- Every completed target has the required account/device coverage and visible evidence.
- Seven-device benchmark reports measured throughput separately from projection; promotion requires per-device mean below 6.5 seconds and P90 below 8.64 seconds, with no identity, route, action, or coverage failures.
- A 24-hour run reports at least 10,000 unique targets only when durable coverage accounting confirms the result; short canaries are not extrapolated as proof.

## Out of Scope

Browser follow-back, automatic replies, private-channel messaging, proxy selection, and TikTok credential management remain separate systems. This design does not weaken their existing pause state or policy checks.
