# TikPoc AI 产品经理作品集演示数据设计

**日期：** 2026-09-04  
**状态：** 已获用户方向批准，待书面规格复核  
**目标环境：** `https://tikpoc.tikpoc.site`  
**数据类型：** 明确标识的合成演示数据

## 1. 目标

为已部署的 TikPoc 运营台创建一套可重复生成、可清理、可审计的作品集演示数据，使管理后台能够完整展示 AI 产品从获客、意图识别、自动回复、私域邀请、联系方式捕获、人工接管到成交归因的闭环。

本设计服务于 AI 产品经理面试展示。演示重点不是制造完美指标，而是证明产品能够：

1. 把多账号触达与线索承接拆成独立执行面；
2. 区分尝试、确认成功、不确定和失败状态；
3. 通过持久化计划、租约和状态机控制 AI 自动化风险；
4. 将 AI 效果连接到私域转化、人工接管和销售结果；
5. 用运营台提供可解释、可追踪的产品证据。

## 2. 演示故事

演示项目名称统一使用：

`DEMO · AI 多账号获客转化试点`

演示周期为连续 14 天，业务链路为：

`目标池 → 7 账号协同触达 → 关注与入站消息 → AI 意图识别 → AI 多轮回复 → 私域邀请 → 联系方式捕获 → 人工接管 → 成交归因`

所有演示实体使用 `demo-` 或 `DEMO` 前缀。任何可能被误解为真实生产结果的名称、联系方式、账号标识或对话内容都使用合成值。

## 4. 演示实体

### 4.1 轮次与目标池

- 创建一个演示目标池和一个主获客轮次；
- 主轮次覆盖 7 个演示设备与账号；
- 生成 14 天时间分布，使趋势图能够呈现启动、增长、稳定和收敛阶段；
- 生成少量历史已完成轮次，供轮次选择器切换；
- 目标标识使用 `demo_target_00001` 形式；
- 不导入真实用户数据。

### 4.2 设备与账号

创建 7 个演示设备和账号映射：

- `demo-device-01` 至 `demo-device-07`；
- `demo-account-01` 至 `demo-account-07`；
- 6 个设备处于健康状态；
- 1 个设备保留可解释的轻微预警；
- 每个设备包含访问量、完成量、异常量、平均耗时和 P90 耗时；
- 覆盖数据体现接近完成但仍有少量缺口的真实运营状态。

### 4.3 线索与会话

至少生成 20 条可在收件箱中直接查看的代表性线索，覆盖：

- 中文购买咨询；
- 英文产品咨询；
- 首轮 AI 回复；
- 第二轮购买信号；
- WhatsApp 或 Telegram 邀请；
- 联系方式捕获；
- 明确要求人工客服；
- 价格、退款、投诉或取消场景；
- 一条保持 busy 的 `uncertain` 发送；
- 一条完成对账的 `sent` 发送；
- 一条被替代的 `superseded` 计划。

线索标识使用 `demo_lead_001` 形式。对话内容保持自然、简洁、中英文混合，并只使用合成的品牌、商品、价格占位和联系方式。

### 4.4 自动化设置

为 7 个演示账号创建运行时展示配置：

- 品牌名称；
- Offer 上下文；
- FAQ 上下文；
- 回复语气；
- AI 开关；
- 自动回关开关；
- WhatsApp 或 Telegram 渠道状态。

Provider API Key 保持空值。私域地址使用明显的演示占位值，不使用真实号码、用户名或邀请链接。

### 4.5 成交归因

成交记录使用模拟订单标识与模拟金额。经营分析应能连接：

- 来源账号；
- 首次触达时间；
- 入站消息；
- AI 回复计划；
- 私域邀请；
- 联系方式捕获；
- 人工接管；
- 模拟成交结果。

若当前持久化模型尚未包含独立成交实体，则只使用现有漏斗事件表达模拟成交，不扩展与本任务无关的新业务系统。

## 5. 生成方式

实现一个独立、可测试的演示数据生成入口，优先复用现有 repository、service 和数据库迁移接口，不通过散落的生产数据库 SQL 手工修改。

生成器要求：

1. 固定随机种子，保证每次生成相同数据；
2. 使用唯一演示命名空间；
3. 支持重复执行且不产生重复记录；
4. 只处理属于该演示命名空间的数据；
5. 支持预览、生成、清理三个动作；
6. 输出创建、复用、跳过和清理数量；
7. 失败时事务回滚，不留下半套数据；
8. 不读取或输出现有密钥与浏览器认证状态。

建议 CLI 结构：

```bash
uv run tikpoc demo-data preview --db PATH
uv run tikpoc demo-data seed --db PATH
uv run tikpoc demo-data clear --db PATH
```

最终命令名以现有 CLI 结构和测试约定为准，但必须保留等价的预览、生成和清理能力。

## 6. 安全与运行边界

- 演示数据写入服务器的持久化 TikPoc 数据卷；
- 生成前创建数据库时间戳备份；
- 移动任务执行器保持停止；
- Chrome 自动回复 Worker 保持停止；
- 不触发真实消息发送、关注、点赞、收藏或转发；
- 不配置真实 Provider Key；
- 不配置真实私域目的地；
- 不存储真实个人信息；
- 保留当前 Caddy 登录保护和 HTTPS 配置；
- 不修改或重启服务器上的 NexaPanel 与量化服务；
- 部署时只更新 TikPoc 管理后台容器和对应数据卷。

## 7. 页面预期

### 7.1 运营监控

- 不再显示“暂无获客轮次”；
- 轮次选择器至少包含主演示轮次与历史轮次；
- 展示 7 个设备和账号；
- 展示覆盖、完成、异常和耗时指标；
- 能解释 1 个预警设备与少量覆盖缺口。

### 7.2 线索收件箱

- 至少显示 20 条代表性线索；
- 覆盖 `new`、`engaged`、`qualified`、`invited`、`contact_captured`、`human_required` 和 `closed`；
- 能进入会话查看中英文多轮记录；
- `uncertain` 会话保持忙碌语义，避免表现为可立即重发。

### 7.3 经营分析

- 显示 14 天趋势；
- 显示触达至模拟成交的漏斗；
- 显示账号贡献和 AI 自动处理指标；
- 汇总数字与明细记录一致。

### 7.4 自动化设置

- 显示 7 个账号；
- 每个账号有演示用业务上下文和开关状态；
- API Key 显示为未配置；
- 设置页仍可正常读取和保存合成配置。

## 8. 测试与验收

### 8.1 自动化测试

- 生成器首次执行测试；
- 重复执行幂等测试；
- 清理只删除演示命名空间测试；
- 中途异常事务回滚测试；
- 汇总指标与明细一致性测试；
- CLI 预览、生成和清理测试；
- 现有 Python、前端和静态检查回归。

### 8.2 服务器验收

1. 备份当前服务器数据库；
2. 部署经测试的生成器；
3. 执行预览并保存数量摘要；
4. 执行生成；
5. 检查容器健康状态与日志；
6. 检查首页、状态、设置和线索 API；
7. 重启 TikPoc 容器并确认数据保留；
8. 检查 NexaPanel 服务状态未受影响。

### 8.3 浏览器验收

- 使用正式域名和真实 Chrome 打开四个后台页面；
- 检查页面可见状态，而不是只依赖 HTTP 状态；
- 检查 Console 和失败请求；
- 核验轮次切换、线索筛选、会话查看和设置读取；
- 在桌面视口下保留适合作品集使用的最终页面。

## 9. 作品集交付

数据验收完成后提供：

1. 推荐截图顺序；
2. 每张截图的短标题和说明；
3. 一段可直接粘贴进作品集的项目描述；
4. 项目背景、用户、目标、本人职责、核心机制、关键决策和量化影响；
5. 演示数据口径说明，明确数字用于展示产品流程与指标体系。

## 10. 完成标准

以下条件全部满足后，本任务才算完成：

- 演示数据生成器经过红绿测试并通过完整适用回归；
- 演示数据可重复生成和清理；
- 正式后台四个页面均有可解释内容；
- 汇总数据与明细一致；
- 移动端和浏览器自动 Worker 未因演示数据启动；
- 数据在容器重启后保持；
- 正式 HTTPS 域名、登录保护和既有服务保持正常；
- 已完成真实浏览器可见状态验收；
- 已交付作品集截图顺序与文案。
