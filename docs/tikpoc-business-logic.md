# TikPoc 获客业务逻辑

**文档状态：** 当前业务口径与运行基线  
**更新时间：** 2026-07-21
**适用范围：** 多账号移动触达、浏览器承接、AI 客服、私域导流、人工成交与经营漏斗

> 当前运行已切换到 B 策略：原始去重目标池按短批次集中触达，并保留原任务、设备和持久化断点。策略只改变调度顺序，不改变资格、互动、额度、核验、幂等或 N/N 覆盖口径。

## 1. 业务目标

TikPoc 的目标不是单纯完成访问量，而是把一批去重潜在客户持续送入可衡量的成交漏斗：

`目标用户 -> N/N 账号触达 -> 访问主页 -> 关注或私信 -> AI 对话 -> 明确兴趣 -> 引导查看主页联系方式 -> 联系方式沉淀 -> 人工成交 -> 销售额`

系统分成两个互不抢占的执行面。移动端负责主动触达，浏览器端负责承接关注、私信和后续对话。移动任务不因浏览器消息处理而暂停；浏览器任务也不操作移动端页面。

账号数量是配置项，不在代码中写死。正式容量基准按 7 个账号计算，即每日处理 10,000 个唯一目标并完成 70,000 次已确认账号访问；其他账号数量使用同一套 N/N 逻辑。

### 1.1 当前业务优先级

1. 保证移动端持续、稳定、可恢复地完成目标池触达；
2. 保证符合资格且动作到期的用户真实完成互动，不能为了速度降级为纯留痕；
3. 记录访问、互动、关注、私信、有效对话、联系方式和成交漏斗；
4. 浏览器自动回关和自动回信继续保留架构与数据契约，但当前不抢占移动触达主任务；
5. 所有性能优化必须证明没有改变资格、动作、核验、幂等和覆盖口径。

## 2. 输入、去重与身份

输入是评论用户 CSV。导入时使用结构化 CSV 解析，保留原始行号与来源信息，并按以下优先级生成目标身份：

1. `sec_uid`；
2. `user_id`；
3. 仅在稳定 ID 都缺失时使用规范化用户名。

同一个人即使在源文件中出现多次，也只创建一个逻辑目标。源行仍作为 lineage 保存，便于回溯。目标池导入后保持不可变；需要再次触达时创建新轮次，不覆盖旧轮次结果。

每个启用账号都获得同一目标池的一份 assignment，因此一个目标在 N 个账号下形成 N 条独立任务。各设备使用持久化种子生成不同且可恢复的顺序，避免同时访问同一个目标，也避免重启后顺序漂移。

## 3. 移动端触达规则

### 3.1 主页确认

每次触达先打开目标主页，再通过屏幕上可见的用户名和主页结构确认身份。ADB 或 Appium 命令成功、深链已发送、HTTP 返回成功，都不等于访问成功。

只有可见身份匹配后，系统才记录 `profile_visit_confirmed`。身份不符、页面仍停留在上一用户、未知页面或路由失败都进入明确的失败或延期状态，不计入覆盖。

### 3.2 资格判断

当前批准规则是：

```text
following > followers AND video_count >= 1
```

也就是关注数必须大于粉丝数，并且至少有 1 个可见视频。旧的“视频大于 3 个”规则已经废止。

主页 XML 若把视频数解析为 `0`，但关注与粉丝关系满足条件，设备会额外执行一次语义视频容器查询。只统计当前可见的容器，并缓存同一组元素供后续选视频和点击；隐藏、失效或真正为空的结果仍按 `0` 处理。

每个目标在同一轮次只发布一份资格快照。首台到达设备读取并发布关注数、粉丝数、视频数和访问状态；其他设备仍需在自己的屏幕上确认目标身份，然后可以复用资格判断。每台设备仍独立选择视频和动作。

### 3.3 视频与互动

符合资格时，设备从当前可见视频中确定性随机选择一个视频并打开。视频必须通过可见控件确认已经打开，之后才进入互动步骤。

互动采用每账号、每动作的滚动一小时节奏：

| 动作 | 每账号滚动 1 小时上限 |
| --- | ---: |
| 点赞 | 100 |
| 收藏 | 14 |
| 转发 | 25 |

每种动作使用持久化 token bucket 和滚动额度判断当前是否到期。多个动作同时到期时进行持久化的确定性加权选择；没有动作到期时，本次为 `trace-only`。这使动作分散在整小时内，而不是在小时开始集中消耗。

计划一经创建不可变。重试沿用原视频、原请求动作和原额度证据，不重新抽取。`planned`、`executing`、`uncertain` 和 `confirmed` 都占用滚动额度，防止重启或结果不确定时超限。

### 3.4 动作确认

- **点赞：** 可见控件必须进入已点赞状态。
- **收藏：** 可见控件或校准后的图标像素必须确认已收藏。
- **转发：** 必须打开分享面板，点击其中可见的 Repost 控件，并确认 Reposted 或等价完成状态。
- **纯留痕：** 确认目标主页或计划视频已访问，不点击互动控件。

只打开分享面板不算转发。分享面板完整出现但没有 Repost 控件时，记录 `repost_unavailable`，释放这次转发额度，并把已确认视频访问保留为纯留痕；不得伪造转发成功。

### 3.5 纯留痕的含义

以下情况会得到纯留痕结果：

- 主页不满足资格规则；
- 符合资格但当前没有动作到期；
- 计划就是留痕；
- 已确认视频访问，但 Repost 在可见分享面板中不可用。

因此，“没有互动”不一定是漏做。判断是否正确必须同时查看资格快照、动作计划、quota/pacing 原因和最终证据。若主页实际有视频却被错误记录为 `post_count=0`，则属于识别缺陷，不应被解释为正常纯留痕。

### 3.6 速度与互动成本

当前六设备真实运行表明，主页纯留痕通常约 4 秒；点赞、收藏和转发因为需要进入视频并验证可见结果，通常约 14、17 和 20 秒。互动路径天然比纯留痕慢，尤其是转发必须经过分享面板和结果确认。

速度优化优先处理异常长尾、重复页面树读取、无效等待、代理故障、Appium 会话卡顿和设备差异。正常可见点击、动作后核验、身份确认和配额控制属于业务成本，不以删除这些步骤换取吞吐。

## 4. 多设备覆盖与恢复

每个 assignment 都有独立的阶段、租约、计划、尝试和结果。一个设备/账号同一时刻只允许一个 worker 持有，两个 worker 不得操作同一账号。

系统分别记录访问覆盖和执行终态：

- `profile_visit_confirmed`：已经在该设备上看见并确认目标主页身份，是正式 N/N 访问覆盖口径；
- `assignment_completed`：该 assignment 已经耗尽自动处理。通常表示留痕或互动达到可验证终态；若唯一一次 reconciliation 后仍为 uncertain，或已确认访问后来无法重开未完成目标，则只表示自动重试终结，不能解释为互动确认成功。

正式 `N/N` 覆盖以 durable confirmed visits 为准。创建任务或尝试导航不计覆盖；一个 deferred assignment 可能已经确认主页访问，但其互动终态仍未完成，因此覆盖率和 assignment completion 必须分列展示。

普通慢页面会在本地执行有界恢复，包括重新检查、返回基线、重启 TikTok 或重建 Appium 会话。动作结果不确定时只读取当前状态进行一次 reconciliation，禁止再次点击可能会切换状态的控件；仍不明确时保留 action plan 和 quota 的 uncertain 状态并终结该 assignment 的自动重试。容量与推广审计必须继续把它列为未确认互动。

首次 assignment claim 仍停留在 `profile_opening`、没有 confirmed visit，并且身份确认失败后可见页面明确报告账号 `missing` 或 `suspended`、可见用户名也与当前目标一致时，记录该设备 assignment 为 `profile_unreachable/skipped`。空用户名、上一目标残留、普通路由失败、`Something went wrong`、加载不完整、观察读取异常和指标读取产生的 `inaccessible` 都继续 deferred，并保留实际异常类别，因为它们可能是设备或网络故障，不能当成目标账号失效。该结果不跨设备传播，其他启用设备仍保留并执行自己的 assignment。已确认访问后来无法重开未完成目标时保留访问证据、记录明确失败并终结自动处理，不伪造互动成功；其他 `ProfileIdentityMismatch` 和视频/动作失败继续 deferred。可见且类型明确的 private 主页按身份确认后的 trace 处理，不归入 skipped。skipped 不计 N/N 覆盖；运营耗尽可用 `completed + skipped` 判断 worker 是否还有可处理任务。

### 4.1 批次策略

- **A 策略：** 所有设备对同一个完整目标池执行各自确定性乱序，持续运行直到全量 assignment 耗尽。优点是断点简单、设备可独立推进。
- **B 策略（当前运行）：** 把目标池按约 1,000 个逻辑用户拆成短批次，所有设备优先完成当前短批次，再进入下一批。目标是让同一批用户在更短时间窗口内获得多账号触达。
- B 策略不改变任何目标资格、动作选择、额度、可见核验或 N/N 覆盖规则。运行期间继续与 A 策略对比转化率、吞吐、失败率和设备空闲率。

### 4.2 直播兴趣用户插队

直播间采集器可以把当前在线且与产品相关的用户作为 FIFO 插队批次提交。系统先让各设备完成已经持有租约的当前用户，再由所有参与设备完成最早的插队批次；快设备在全设备屏障等待，不提前返回原任务。多个插队批次按提交顺序执行，全部完成后从普通大任务原有 assignment、attempt 和乱序断点继续。

插队批次沿用当前普通轮次的设备账号快照，每台设备仍使用不同的持久化乱序种子。同一设备账号在本轮已确认访问的身份不会重复触达：普通任务的 confirmed visit 可以满足插队 assignment，插队 confirmed visit 也可以满足该设备尚未开始的普通 assignment 和后续重复插队 assignment。该传播只接受明确 confirmed visit；skipped、deferred/uncertain、缺少访问证据或稳定身份冲突都不传播，也不跨设备账号传播。

采集 AI 通过 `priority-import` 提交完整 JSONL/XLSX 文件，通过 `priority-status` 读取 FIFO 状态、逐设备 pending/deferred/completed/skipped 和普通任务断点。采集程序必须先写临时文件、关闭并原子重命名，再调用 CLI；读取期间变化的文件会被拒绝。详细机器合同见 `docs/priority-live-batch-cli.md`。

## 5. 浏览器线索承接

本节描述已实现并通过自动化验证的业务契约。真实账号环境仍需要分别完成欢迎私信、自动回复、页面重载幂等、联系路径、联系方式沉淀和浏览器 heartbeat 等可见状态门槛；自动化测试或 HTTP 成功不代表这些 live gates 已经通过。

每个 TikTok Web 账号使用独立 Chrome Profile，并与一个 `account_id`、`device_id`、预期 TikTok 用户名绑定。Activity 和 Messages 页面从可见 DOM 读取状态，扩展不读取 Cookie、浏览器凭据、会话 token 或 Chrome Profile 数据库。

所有点击和发送都必须经过本地 Python 服务的账号级独占租约。重复标签页、DOM 重绘、扩展重启和重复 HTTP 请求必须复用同一幂等证据。

### 5.1 新关注者

1. Activity 页面先把历史可见行建立为 baseline，不处理旧记录。
2. DOM 变化或 watchdog 发现新的关注者行。
3. 可见关注语义、用户主页链接和 Follow/Follow back 控件必须同时明确。
4. 扩展申请 `followback` 租约并点击一次。
5. 按钮变成 Following/Friends 等可见完成状态后，才记录回关完成。
6. 开启欢迎语时，完成的回关为该账号与关注者创建一份不可重复的 welcome plan。

欢迎私信只发一次，介绍配置的品牌 AI 客服身份，感谢关注，并问一个低门槛的产品兴趣问题。已有会话或已有收发消息会抑制通用欢迎语；新入站消息优先于欢迎任务。

### 5.2 入站私信与 AI 回复

Messages 页面为每条最新入站消息生成账号级 fingerprint。一个 fingerprint 最多创建一份持久化回复计划，第一次生成的草稿不可变，重试不得再次调用模型产生不同文本。

回复规则：

- 使用客户当前语言；
- 通常 1 到 3 个短句；
- 先回答当前问题，再提出最多 1 个资格问题；
- 只使用账号配置的产品、FAQ、语气和品牌事实；
- 不编造价格、库存、发货、折扣、支付、退款或承诺；
- 默认每个会话最多 12 条自动回复；
- 购买意向或达到有效对话阈值后，引导客户查看 TikTok 主页链接或置顶帖联系方式；
- 联系方式被客户主动发送时，持久化 contact-captured 事件并确认收到；
- 明确要求停止联系时，生成空的 `closed` 计划，不调用 AI、不发送后续消息，并抑制待发欢迎语。

支付、退款、投诉、取消、额外折扣或要求代表处理等超出配置事实的问题，不做决定或虚构人工在线状态；回复能力边界，并引导到主页联系方式。邀请/联系引导采用 24 小时冷却，避免重复催促。

发送前扩展重新确认账号、会话和最新入站 fingerprint。文本通过受信任的浏览器输入路径写入，发送后必须看见完全匹配的 outbound bubble。看不见明确结果时记录 `uncertain` 并保持忙碌，等待 reconciliation 或租约过期，避免重复发送。

## 6. 漏斗与经营指标

系统至少记录以下账号级、目标级和会话级事件：

| 阶段 | 业务含义 |
| --- | --- |
| 访问触达 | 某账号确认到达并匹配目标主页 |
| N/N 访问覆盖 | 同一目标被所有启用账号确认访问 |
| Assignment 完成 | 留痕或互动达到可验证终态 |
| Follow | 目标关注账号或被回关 |
| DM inbound | 收到客户私信 |
| Engaged | 产生有效对话 |
| Qualified | 出现产品或购买信号 |
| Contact route | 已引导查看主页联系方式 |
| Contact captured | 客户提供联系方式或明确接受联系路径 |
| Human/closing | 进入人工成交或例外处理 |
| Sale | 成交、金额和归因被人工确认 |

经营分析必须同时展示数量和转化率，不能只看触达速度。建议主漏斗为：

`唯一目标数 -> N/N 访问覆盖数 -> Assignment 完成率 -> 新关注数 -> 入站私信数 -> 有效对话数 -> 合格线索数 -> 联系方式沉淀数 -> 成交数 -> 销售额`

## 7. 容量与质量门槛

七账号正式基准：

| 指标 | 门槛 |
| --- | ---: |
| 每日唯一目标 | 10,000 |
| 每日已确认设备访问 | 70,000 |
| 每设备每日目标 | 10,000 |
| 24 小时平均预算 | 8.64 秒/目标 |
| 20 小时平均预算 | 7.20 秒/目标 |
| 推广门槛 | 单设备 mean < 6.5 秒，P90 < 8.64 秒 |

速度门槛必须与身份匹配、可见动作确认、滚动额度、租约互斥、幂等和 N/N 覆盖一起通过。短时间样本或单元测试只能提供测量依据，不能据此声称全天产能已经达成。报告必须区分 measured throughput 与 projected throughput。

## 8. 运行断点原则

生产轮次使用持久化 round、assignment、计划和租约继续执行。暂停与恢复不得重新导入同一目标池、创建重复 assignment、重写历史 confirmed visits 或重新抽取既有动作计划。

精确的本机路径、数据库位置、round ID、文件 checksum、账号数量和实时状态计数只记录在受控内部 runbook，不进入公开业务文档。恢复前由运营人员在内部核对输入 checksum、round 状态、pending/deferred/completed/skipped 数量、设备健康和 worker fence。

## 9. 数据与运行原则

SQLite 是当前移动轮次、动作节奏、租约和本地浏览器会话的运行事实源。Supabase 已部署中心化表结构，并已接入目标池、账号映射和设备健康等部分数据；线索、事件、销售和同步检查点的完整生产同步仍属于后续集成范围。任何同步都不能绕过本地事务边界，也不能让线索阶段回退。

滚动动作额度与 pacing 保存在选定 SQLite 中。实时账号不得通过切换新数据库清空历史额度。需要新工作量时，在同一个持久数据库中新建 pool/round；如确需使用全新数据库，必须先核对所有旧数据库，并从最后一次非 trace 证据起完成连续 60 分钟无动作冷却。

密钥、密码、Cookie、token、真实联系方式、私域目的地、消息正文和含个人数据的截图不得进入 Git、测试输出或公开文档。GitHub 用于版本、提交、评审和回滚，不存放运行数据库、CSV、Chrome Profile、日志或秘密配置。

- [ ] 从原 round 恢复并先执行短 canary，确认新识别规则确实产生互动计划。
- [ ] canary 无身份错配、重复点击、额度超限、长期租约或异常吞吐回退。
- [ ] canary 通过后继续剩余任务并持续监控漏斗、速度和失败分类。
- [ ] 浏览器账号身份、Activity/Messages heartbeat 和剩余 live gates 分别验证。

## 11. 不可改变的业务边界

- 不因追求速度降低 `following > followers AND video_count >= 1` 的资格判断。
- 不把本应执行的点赞、收藏或转发改成纯留痕。
- 不取消身份、视频打开、互动结果和转发结果的可见状态核验。
- 不通过重复点击处理 uncertain；只做一次状态核验，然后保留证据并延期。
- 不把一台设备的无法访问结论传播到其他设备。
- 不把 skipped 计入 confirmed coverage。
- 不为性能优化新增不必要的 Inbox 跳转、额外页面分支或重复 TikTok 重启。
- 不用短时间峰值替代长期 measured throughput，也不把 projected throughput 写成已经达成。
