# TikPoc 项目耦合与业务风险审查

日期：2026-07-21  
审查分支：`feat/web-lead-conversion`  
运行轮次：`round-ae3616f70853b1901e95`

## 1. 审查目标

本次审查围绕当前获客业务的四条不可退让原则展开：

1. 目标主页身份必须经过可见状态确认；
2. 规则始终是 `following > followers` 且可见视频数 `>= 1`；
3. 合格用户按既定配额选择点赞、收藏、转发或仅留痕，互动必须核验；
4. 速度优化不得削弱身份、互动、幂等、账号隔离和覆盖统计。

审查期间六设备继续执行原 CSV 和原轮次。本文件只记录证据、风险和整改顺序，不在生产轮次中推动大范围重构。

## 2. 执行结论

当前系统的持久化断点、设备围栏、动作计划和覆盖统计基础是可靠的，没有发现 Python 模块导入环。项目可以继续处理当前批次，但还不适合把短时运行结果直接当作正式容量结论。

最高价值问题不是增加更多功能，而是提高互动动作在不同设备上的真实成功率，并让“健康”状态能够反映业务是否持续前进。当前应先处理互动可靠性、进度监控和失败证据，再做仓储与模块拆分。

审查未发现需要立即停止整个轮次的数据破坏问题。现有 `uncertain` 和人工重试保留机制避免了把未确认互动误报为成功，也避免了无上限自动重试；代价是部分合格目标只留下确认访问，没有完成原计划互动。

## 4. 分级发现

### I-1：互动点击在设备之间存在显著不一致

**级别：Important，直接影响业务。**

**证据**

- 同一代码和规则下，slot-03/06 的点赞确认稳定，而 slot-01/02/04/05 出现大量 `uncertain`。
- 失败现场截图显示点赞心形保持白色，说明动作没有真正应用，而不是单纯核验文本失效。
- WebElement `click()` 和基于元素 ID 的 `mobile: clickGesture` 都可能返回成功响应但没有改变可见状态。
- 原生元素手势试验未通过实机门禁，代码提交已回退；当前分支没有把无效试验保留为正式修复。
- 系统会进行一次重新核验，然后把仍未确认的计划放入人工重试保留，不会把它伪装成成功。

**业务影响**

- 合格目标的确认访问仍然保留，但原计划互动缺失；
- 失败设备的单机速率下降到约 223–279 用户/小时；
- 如果只看 completed，会高估“访问并互动”的实际质量。

**建议**

1. 在一个失败设备上校准真正可点击的父节点或屏幕坐标手势；
2. 以可见红心、收藏状态或转发结果为唯一通过门槛；
3. 先做单设备 20 次连续点赞门禁，再扩展到六设备；
4. 保留一次核验和人工重试策略，不增加盲目点击次数。

### I-2：设备健康状态没有业务进度心跳

**级别：Important，影响故障发现和速率判断。**

**证据**

- `fleet_device_health` 只在工作进程启动、退出或状态转换时写入；
- 工作进程持续处理任务时不会刷新 `updated_at_ms`；
- 此前出现零完成的重试风暴时，六设备仍显示 healthy；
- 本次运行超过 1,000 秒后健康时间仍停留在启动时刻。

**业务影响**

- 运营台可能把“进程活着但没有产出”显示为健康；
- 网络、Appium、页面卡住或重复重试只能靠人工观察发现；
- 无法稳定触发低速告警或自动暂停单台异常设备。

**建议**

- 将进程存活、设备连通和业务前进拆成三个指标；
- 每次完成、延后或跳过后记录 `last_progress_at_ms`、最近窗口完成数和当前阶段；
- 以 5 分钟无进度、uncertain 比例和阶段滞留时长生成 degraded 状态。

### I-3：失败诊断证据不足

**级别：Important，延长实机问题定位时间。**

**证据**

- `AppiumTikTokDevice.capture_diagnostics()` 只保存页面 XML 前 2,000 个字符；
- 动作控件通常位于 XML 后部，截断后看不到点赞、收藏和分享状态；
- 当前动作记录的 `screenshot_path` 经常为空；
- Appium 异常时只留下 `diagnostic capture failed`。

**业务影响**

- 相同问题需要重复人工截图；
- 难以区分点击无效、控件被遮挡、页面已跳转和核验选择器失效；
- 设备差异无法形成可复用的证据库。

**建议**

- 失败时保存受控目录内的截图、当前 activity、窗口尺寸、关键控件语义与 bounds；
- XML 只保存脱敏后的关键节点，不保存无界完整页面；
- 诊断失败本身写入独立错误码，避免覆盖原始业务错误。

### I-4：同一 SQLite 文件存在多套数据访问边界

**级别：Important，影响长期维护。**

**证据**

- `db.py` 3,835 行，`acquisition_db.py` 3,715 行；
- `Database`、`AcquisitionRepository`、`AcquisitionService` 都对同一 SQLite 文件承担迁移或直接 SQL；
- API 启动时依次调用三套迁移入口；
- `AcquisitionService` 绕过部分 repository 边界直接建立 SQLite 连接。

**业务影响**

- 事务归属和迁移顺序不够清晰；
- 新增 Supabase 或多进程部署时容易产生双写、锁竞争和行为漂移；
- 一次字段变化需要跨多个巨型文件同步。

**建议**

- 当前 CSV 完成前保持数据库执行路径不变；
- 后续按领域拆分 schema migration、acquisition repository、browser/lead repository 和 query service；
- API 和命令行只依赖明确的 service 接口，不直接拼接跨域 SQL。

### I-5：设备适配器同时承担移动触达和旧 Inbox 功能

**级别：Important，存在业务平面串扰风险。**

**证据**

- `device.py` 同时包含主页访问、视频互动、回关、新粉丝问候和 Inbox 回复；
- 生产 Fleet 已不再使用 Inbox 路由恢复，但旧 `runner.py --event-driven` 仍可调用这些方法；
- 一个类同时实现两套页面状态机，选择器和恢复行为共享同一 Appium 会话。

**业务影响**

- 后续维护旧入口时可能重新把移动任务带到 Inbox；
- 页面恢复、缓存和账号状态的改动容易跨业务平面产生副作用。

**建议**

- 当前批次只保持生产 Fleet 不调用旧方法；
- 批次完成后拆成 `MobileAcquisitionDevice` 和独立的历史/浏览器线索处理适配器；
- 下线或显式隔离 `--event-driven` 旧入口。

### I-6：租约丢失的子进程退出语义仍有缺口

**级别：Important，影响异常恢复。**

**证据**

- 工作树中已有两个尚未归入当前任务的失败测试，分别覆盖“assignment owner 已被替换”和“子 worker 丢失 fence 后应干净退出”；
- `run_device_worker()` 当前会让 `DeviceWorkerLeaseLost` 穿透子进程；
- `claim_next_assignment()` 对过期 assignment owner 的回收依赖外部恢复步骤，不是一次原子接管。

**业务影响**

- 网络抖动或主进程重启后可能产生 child_exit 和额外 supervisor 重启；
- 旧 worker 的迟到写入虽会被 fence 拦截，但会增加恢复噪声和停顿。

**建议**

- 将 fence loss 定义为预期终止路径，关闭 driver 后以明确退出状态返回；
- 在 claim 或独立恢复事务中原子回收已过期 assignment lease；
- 保留所有终端写入的 owner/fence 校验。

### M-1：人工重试时间戳不是 JavaScript 安全整数

**级别：Moderate。**

`MANUAL_RETRY_AT_MS = 2**63 - 1` 适合 SQLite，但超过 JavaScript 安全整数。未来通过前端或 Supabase 序列化时可能发生精度损失。建议迁移到明确、可读且 JS 安全的远期时间戳，并为已有记录做一次迁移。

### M-2：不同工作树的业务规则文档存在漂移

**级别：Moderate。**

主检出目录的 `AGENTS.md` 仍写 `video_count > 3`，活跃工作树和 `rules.py` 已是 `video_count >= 1`。实际生产逻辑正确，但未来代理从主检出目录开始工作时可能重新引入旧规则。建议在合并分支时同步控制文档，并让规则测试成为唯一可执行事实。

### M-3：Supabase 仍不是执行事实来源

**级别：Moderate。**

当前 SQLite 仍是设备租约、动作计划和覆盖统计的执行真相。Supabase 迁移应作为独立项目推进，先定义事务、锁和 fence 等价语义，再迁移数据；不应在当前长批次中边跑边切换。

## 5. 暂不处理的低价值重构

以下事项不应打断当前 CSV：

- 仅为了缩短文件而拆文件；
- 重命名现有模型或表；
- 把 SQLite 立即替换成 Supabase；
- 修改已经稳定的身份、快照、配额或覆盖逻辑；
- 通过降低核验次数、跳过互动或增加盲目点击来换取表面速度。

## 6. 建议执行顺序

### P0：当前批次运行期间

1. 保持原轮次、原断点和六设备继续运行；
2. 增加独立监视查询，按设备统计 5 分钟完成数和 action confirmed/uncertain；
3. 对 uncertain 比例异常的设备保留现场证据；
4. 不自动重试人工保留任务，不重复触达同一视频。

### P1：下一个小型修复窗口

1. 单设备解决真实点赞触发面，完成 20 次连续可见核验；
2. 增加业务进度心跳和 5 分钟无进度告警；
3. 补齐失败截图、activity 和控件 bounds；
4. 修复 fence loss 的干净退出与过期 assignment lease 回收。

### P2：当前 CSV 完成后

1. 拆分移动触达与旧 Inbox 设备适配器；
2. 收敛 SQLite migration 和 repository 边界；
3. 同步主检出目录与活跃分支的业务规则文档；
4. 单独设计 Supabase 迁移和回滚门禁。

## 7. 验收标准

后续整改不能只以单元测试通过作为完成标准，至少需要：

- 每台设备连续 20 次计划互动均得到可见终态或明确 unavailable；
- 没有 Inbox 跳转、跨账号 worker、重复视频动作或错误完成记录；
- 5 分钟窗口可以识别零进度设备；
- uncertain 只核验一次并进入人工保留；
- 六设备稳定窗口平均达到业务目标，同时分别报告实测值与投影值；
- 完整 Python、Node、Android、Ruff 和差异检查通过。

## 8. 最终判断

项目的核心业务建模方向正确：访问证据、互动计划、配额、动作核验、覆盖统计和设备 fence 都有明确持久化边界。当前主要瓶颈是实机动作适配和运行可观测性，而不是业务规则设计。

因此应让当前任务继续跑，同时优先收集真实互动失败证据；下一次代码窗口只处理 I-1、I-2、I-3 和 I-6。数据库拆分、旧入口隔离和 Supabase 迁移放到当前 CSV 完成之后。
